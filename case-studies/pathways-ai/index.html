02

The Problem and How AI Helps

  • A college student pivoting away from a four-year degree wants to know which programs exist and whether they're eligible.
  • A career changer who needs steady income soon applied weeks ago and hasn't heard anything.
  • An applicant has a problem that no FAQ covers and needs to reach a real person.

Pathways AI answers the routine questions, shows applicants where they stand, and passes everything else to staff, so the team behind Pathways can spend its time on people.

Three assistance tracks I modeled for the MVP

PUBLIC

Program guidance

Ask about programs and admission requirements.

VERIFIED ONLY

Application status

Verify who you are, see where your application stands, and learn what to do next.

VERIFIED ONLY

Talk to a person

Ask for staff follow-up. The agent collects the details, confirms them, and creates the request.

03

How it works: two decisions

Streamlit chat→Salesforce Agentforce agent→Flows · CRM data · Knowledge · Apex
Salesforce decides. The AI explains.
Decision 1Reliability

What is the AI allowed to decide?

The next step in the conversation comes from a Salesforce formula. The agent only explains it, so it can't invent a requirement or deadline.

  • The formula maps each application stage to a predefined next step.
  • Validation rules keep records complete, for example requiring the missing-documents list when an application is marked Documents Pending.
  • The agent acts through Flows with fixed inputs and outputs, so it can't improvise.
  • Unrelated template topics were removed, so there is less room to route a request the wrong way.
Decision 2Security

What is the AI allowed to reach?

Private information is locked until the visitor verifies with a one-time code.

  • Least privilege: the agent runs as its own execution user with only the access it needs.
  • Object-level and field-level permissions limit which objects and fields it can read.
  • Applicant records are private by default, and program information is public read-only.
  • Verification is separate from the chat text. Typing an email address is not proof, which is why the code step exists.
  • A request is created only after the visitor confirms the details.

05

How I tested it

The check that matters most for an assistant with private data is whether the gate holds. I started with the ideal path: verify, see a limited set of application details, then create a follow-up request. Then I went looking for ways it could break. Here is one of those tests.

One test, start to finish: a frustrated visitor asks for help

Tried
I started a fresh session as a visitor who hadn't verified. In everyday words, not the system's, I said I wanted to file a report because I never got an update on my application.
Expected
The agent asks me to verify first, then collects the details for a follow-up request.
Found
Two problems. The request landed in a template escalation subagent that had no action behind it. After I fixed that, the agent went straight to creating a follow-up request for an unverified visitor, because my own instructions said guests could.
Changed
I deleted the unused escalation subagent instead of building a flow nobody needed yet. I rewrote the instructions so guests can never create a follow-up request. Guests can't be tracked, so open submissions invite abuse, and I haven't built handling for that case.
Retested
A visitor who gave everything up front went through without trouble. A visitor who gave vague details, or asked for things that need verification, was stopped. A verified visitor confirmed the details and a new follow-up request record appeared.

The rest of the testing followed the same layers. I checked the pieces that don't change first, such as the Flows and a small Apex method that supplies the follow-up categories. Then I tested the agent in Agentforce Builder with normal conversations, wrong-way conversations, and odd or incomplete input. Not every scenario passes yet, and automated regression testing is on my list of next steps.

06

Success, scope, and what's next

How I'd know it's working. This is a simulation, so there are no results to report. These are the four things I would track.

Questions answered

People get their answer or finish their request without needing staff.

Correct answers

What the agent says matches the current program information and the applicant's actual record.

Private data stays private

No private record is ever shown to an unverified visitor.

Useful handoffs

Follow-up requests reach staff complete, so nobody has to ask again.

How I scoped five days.

  • I prioritized the outcome: showing the three journeys working for a person from start to finish.
  • I still tested before building on top, starting with the pieces that don't change and then the agent.
  • I scoped the testing too. Quick Execute Anonymous checks stood in for formal unit tests.
  • I deferred, on purpose: a regression suite, audit logging and monitoring, rate and cost planning, the separate API user, and requests from guests. Guests can't be tracked, so for now only verified applicants can submit one.
PLANNED · NEXT ITERATION

When the knowledge base and the CRM disagree

Right now the knowledge documents and the CRM tell the same story: two active programs. Real organizations don't stay that tidy. Programs get retired, paused, or announced before anyone creates a record, and the old guides stay in the knowledge base. Next I'll add programs to the documents that are inactive or have no CRM record, and test whether the agent offers them as currently available. My plan is to treat active Training Program records as the source of truth for availability and use the documents only for description, so a stale document can't turn into an enrollment offer. I chose this case because this kind of mismatch is easy to miss in a demo and costly after launch. It's one edge case of many, and I didn't try to cover them all in five days.

Engineering notes: design details

IDs and display-only dates pass between Agentforce and Flows as Text, and flags as Boolean, to reduce type mismatches. Records keep their native field types.

Follow-up categories are read from the Salesforce picklist, so changing the picklist needs no prompt edits. I checked the method's output with Execute Anonymous and deferred formal unit tests for this time-boxed prototype.

A Follow-Up Request must belong to the same Contact as its Application, and a validation rule enforces that.

Engineering notes: delivery plan

I planned four sprints: an integration feasibility check, the CRM and core agent, knowledge retrieval and human assistance, and frontend integration with evaluation. Each one had its own test and exit criterion before moving on.
