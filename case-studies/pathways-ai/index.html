The Problem and How AI Helps

  • A college student pivoting away from a four-year degree wants to know which programs exist and whether they're eligible.
  • A career changer who needs steady income soon applied weeks ago and hasn't heard anything.
  • An applicant has a problem that no FAQ covers and needs to reach a real person.

Pathways AI answers the routine questions, shows applicants where they stand, and passes everything else to staff, so the team behind Pathways can spend its time on people.

Three assistance tracks I modeled for the MVP

PUBLIC

03

How it works: two decisions

Streamlit chat→Salesforce Agentforce agent→Flows · CRM data · Knowledge · Apex
Salesforce decides. The AI explains.
Decision 1Reliability

What is the AI allowed to decide?

The next step in the conversation comes from a Salesforce formula. The agent only explains it, so it can't invent a requirement or deadline.

  • The formula maps each application stage to a predefined next step.
  • Validation rules keep records complete, for example requiring the missing-documents list when an application is marked Documents Pending.
  • The agent acts through Flows with fixed inputs and outputs, so it can't improvise.
  • Unrelated template topics were removed, so there is less room to route a request the wrong way.
Decision 2Security

What is the AI allowed to reach?

Private information is locked until the visitor verifies with a one-time code.

  • Least privilege: the agent runs as its own execution user with only the access it needs.
  • Object-level and field-level permissions limit which objects and fields it can read.
  • Applicant records are private by default, and program information is public read-only.
  • Verification is separate from the chat text. Typing an email address is not proof, which is why the code step exists.
  • A request is created only after the visitor confirms the details.
04

Governance at every layer

As a data engineer, governance is where I start. An assistant that serves applicants has to be trustworthy before it can be useful, so I put a control at every layer.

LayerThe questionThe control
InterfaceWho makes decisions?Streamlit only shows the conversation and passes messages along. It never decides.
IdentityWho are you?Guests get public information only. Private information unlocks after an email one-time-code check.
AgentWhat can the AI do? What can it see?Limited to three journeys, with unrelated template topics removed. Access starts read-only on specific fields. Create and edit access is granted only for follow-up requests, because that user story needs it.
AutomationWhat are the rules?Flows and Apex apply the business rules, and a request is created only after the visitor confirms. As many decisions as possible are fixed rules, so the agent never has to make a judgment call on something with one right answer.
DataWho can see what?Least privilege. Records are private by default, and object-level and field-level permissions, assigned to users through permission sets, give each only the access it needs.
05

Testing Builds Credibility

An AI product is only as credible as its testing, and so is its engineer. With five days, I chose the smallest set of tests that still makes a credible proof of concept, and I mapped what a production version would add.

LayerMVP scopeProduction quality
AccessRecords private by default, with object-level and field-level permissions set.Sign in as each type of user and confirm what each can see, read, edit, or create, down to field and record level.
AutomationsFlows and Apex checked for correct, repeatable output. The Documents Pending validation rule checked.Break them on purpose with missing or unexpected data, make failures loud and specific, and stay within Salesforce query and rate limits.
AgentNormal, vague, unusual, and unverified-visitor conversations in Agentforce.Full happy-path, negative-path, and edge-case coverage. How it explains a problem and escalates. Proof it can't reach outside its permissions.
User storiesThe three journeys walked by hand in Agentforce, the way a visitor would.Each journey tested end to end through the real chat interface, including prompt-injection and wrong-person attempts, plus an automated regression suite so every change is rechecked.

An example of testing I did

Tried
As an unverified, frustrated visitor, I asked in everyday words to file a report about an update I never received.
Found
The request landed in an empty escalation subagent. After I fixed that, my own instructions let a guest create a request.
Fixed
I removed the empty subagent and rewrote the instructions so only verified applicants can submit one. Then I reran the guest, vague, and all-details cases.
06

Measuring Success and What's Next

Does it work correctly and safely?

A repeatable set of realistic scenarios, including happy paths, edge cases, and unauthorized requests, compared against expected outcomes for accuracy, reliability, and security.

Does it help applicants and staff?

Self-service completion, time to resolution, and whether follow-up requests reach staff with everything needed to act, compared with a pre-AI baseline in a real pilot.

What would I improve next?

Test conflicts between knowledge documents and live CRM records, expand automated regression and security testing, and add monitoring and audit logging.

This proof of concept hasn't been evaluated with real applicants or staff. These measures would guide a customer pilot.

How I scoped five days. I prioritized showing the three journeys working end to end and tested the foundations first. I deferred a regression suite, audit logging and monitoring, the separate API user, and guest requests, which need their own abuse protection.

PLANNED · NEXT ITERATION

When the knowledge base and the CRM disagree

Right now the knowledge documents and the CRM agree: two active programs. Real organizations drift. Programs get retired or announced before a record exists, and old guides linger. Next I'll add inactive programs, and programs with no CRM record, to the documents and test whether the agent offers them as available. My plan is to treat active Training Program records as the source of truth for availability and use the documents only for description. I chose this case because this kind of mismatch is easy to miss in a demo and costly after launch. It's one edge case of many.

Engineering notes: design details

IDs and display-only dates pass between Agentforce and Flows as Text, and flags as Boolean, to reduce type mismatches. Records keep their native field types.

Follow-up categories are read from the Salesforce picklist, so changing the picklist needs no prompt edits. I checked the method's output with Execute Anonymous and deferred formal unit tests for this time-boxed prototype.

A Follow-Up Request must belong to the same Contact as its Application, and a validation rule enforces that.

Engineering notes: delivery plan

I planned four sprints: an integration feasibility check, the CRM and core agent, knowledge retrieval and human assistance, and frontend integration with evaluation. Each one had its own test and exit criterion before moving on.
